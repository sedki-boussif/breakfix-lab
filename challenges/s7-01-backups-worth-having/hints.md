Read `lab.conf`'s backup section first: BACKUP_REPO, BACKUP_REMOTE, BACKUP_PASSWORD_FILE, BACKUP_MARKER, BACKUP_ALERT_LOG, BACKUP_FINGERPRINT and BACKUP_TIMER. Every path the check looks at is named there, so none of it is a guess.
`restic` is installed. `restic init --repo <path>` creates a repository; `--password-file` keeps the password out of your shell history and out of the repository itself. Set up the local one first and get a single snapshot working before you think about scheduling or off-site.
What to back up: both Postgres databases as dumps, not as data directories — a copied data directory from a running server is not a backup. `pg_dump` for the host databases, `docker compose exec -T db pg_dump` for the stand-in's.
Off-site is a second repository, or a copy of the first. `restic copy` moves snapshots between repositories and keeps them deduplicated; a plain `rsync` of the repository directory also works and is easier to reason about. Either is acceptable; say which you chose and why in the report.
The timer is two units: a service that does the work and a timer that starts it. `OnCalendar=daily` with `Persistent=true`, so a VM that was off at the scheduled time catches up rather than skipping silently.
The dead-man's-switch is the part everyone omits. A second timer, every fifteen minutes, that compares the marker's mtime against BACKUP_MAX_AGE_H and appends a line to BACKUP_ALERT_LOG when it is too old. Test it by stopping the backup timer and backdating the marker — which is exactly what the check does.
