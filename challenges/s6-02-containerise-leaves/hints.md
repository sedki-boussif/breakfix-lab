Dump the data before you touch anything else: `sudo -u postgres pg_dump -Fc leaves > /var/tmp/leaves-before-s6-02.dump`. The custom format (`-Fc`) restores with `pg_restore` and lets you restore selectively, which matters when the first restore attempt goes into the wrong database.
The Dockerfile is shorter than you expect: a `python:3.12-slim` base, `COPY requirements.txt` and `pip install` as their own layer before copying the code (so a code change does not reinstall the world), a non-root `USER`, and a `CMD` that runs the same gunicorn invocation the unit does — bind `0.0.0.0:8081` inside the container, not `127.0.0.1`, or nothing outside the container can reach it.
Publish as `"127.0.0.1:8081:8081"`, with the host IP written explicitly. `"8081:8081"` publishes on every interface, and Docker inserts its own iptables rules ahead of ufw's, so the port is reachable from the network with the firewall still reporting that it is closed. That is s4-04, and it is much easier to cause here than to notice.
The database needs a named volume mounted at `/var/lib/postgresql/data`, and the name has to appear both in the service's `volumes:` list and in the top-level `volumes:` block. Mount it with no top-level declaration and you have an anonymous volume: the data survives `down`, and you will never find which volume it is in.
`depends_on` on its own waits for the container to have *started*, which for PostgreSQL means the process exists and is still replaying WAL. Give the database a `healthcheck` with `pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"` and make the app's `depends_on` use `condition: service_healthy`. Without that pair, the first deploy after every reboot fails with a connection error and then works on the retry, which is the most annoying class of bug there is.
Restore into the container, not the host: `docker compose exec -T db psql -U leaves_app -d leaves < dump.sql`, or `pg_restore` with the custom format. If you connect to port 5432 on the host and it answers, you have just restored into the database you were migrating away from.
Disable the unit, do not only stop it: `sudo systemctl disable --now leaves`. A stopped-but-enabled unit comes back at the next boot and fights the container for 8081. One of them wins, it is not always the same one, and the symptom arrives weeks later looking like s5-06.
Last, flip `LEAVES_MODE` to `compose` in `lab.conf`. Everything in the lab that starts or stops this app reads that value, so until you change it the lab is still issuing `systemctl` commands against a unit you just disabled.
