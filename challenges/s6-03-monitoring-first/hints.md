Decide the shape before you install anything. Prometheus plus node_exporter plus Alertmanager is three services and a lot of YAML, and it is the right answer at thirty rules. Netdata is one package and alerts out of the box. A shell script on a systemd timer is the right answer at three rules on one machine. Whichever you pick, the check only cares that the alerts arrive — so pick for the reason, and write the reason down.
Whatever you build has to append to `$S6_03_ALERT_LOG`, one line per alert, each naming its condition. For Alertmanager that is a webhook receiver pointed at something that appends; for Netdata it is a custom notification method in `health_alarm_notify.conf`; for a script it is `>> "$ALOG"`. A dashboard is not a destination — nobody is woken by a graph.
"Any filesystem" is the hard half of the first rule. `df -P --output=pcent,target` lists every mounted filesystem, and the one that fills is rarely the one you thought to watch. In Prometheus that is `node_filesystem_avail_bytes / node_filesystem_size_bytes < 0.2` with no instance filter; in a script it is a loop over `df` rather than a single `df /`.
Alert on the state *change*, not on the state. A rule that appends a line every cycle while a condition holds produces four hundred lines overnight, and the fourth hundredth is the one that gets filtered. Keep the previous state in a variable or a file and write a line only when it differs — and write one when it goes back, too.
Days left on a certificate: `openssl x509 -in "$TLS_CERT" -noout -enddate` gives a date, and `$(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 ))` turns it into a number you can compare. Prometheus users want the blackbox exporter's `probe_ssl_earliest_cert_expiry`, which measures what a client actually gets rather than what is on disk — a better measurement, and one more service.
Test each rule by causing the condition, not by reading the rule. `truncate -s 500M /tmp/ballast` on a small filesystem, `systemctl stop` something, a seven-day certificate from `openssl req -days 7`. A rule you have never seen fire is a rule you have no reason to believe in, which is the entire point of this mission and of the check.
If nothing arrives, the question is which half is broken: did the rule evaluate, and did the notification get delivered? For Prometheus, the Alerts page shows rules in `pending` and `firing` before Alertmanager is involved at all — if the rule is firing and the log is empty, the problem is the receiver, not the expression.
