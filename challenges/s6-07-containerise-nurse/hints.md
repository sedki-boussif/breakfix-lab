Start by reading s6-02's solution if you have passed it. Three of the four files are the same shape, and the differences are what this challenge is about: two services instead of one, and a frontend whose configuration is compiled in rather than read.
Dump first, as always: `sudo -u postgres pg_dump -Fc nurse > /var/tmp/nurse-before-s6-07.dump`. Then restore it *into the container* — if you connect to 5432 on the host and it answers, you have restored into the database you are migrating away from.
The frontend wants a two-stage Dockerfile: `FROM node:20 AS build` with `ARG VITE_API_URL`, `npm ci` and `npm run build`; then `FROM nginx:alpine` and `COPY --from=build /app/dist /usr/share/nginx/html`. The second stage is what runs, so node never ships to production, and the image is a few megabytes instead of a few hundred.
`ARG` in the Dockerfile and `args:` under `build:` in compose.yaml — not `environment:`. An environment variable on the running service arrives long after the bundle was compiled and does nothing at all. The page loads, looks correct, and shows an empty list while `/api/health/` reports 200, which is s3-02's exact symptom with nobody having caused it on purpose.
Map the frontend as `"127.0.0.1:3000:80"`: port 3000 outside, because that is what the host nginx proxies to and what `NURSE_WEB` names, and 80 inside, because that is where the nginx in the container listens. The two numbers being different is the normal case, not a mistake.
When the stack is up, check the thing the health endpoint cannot tell you: `curl -fsS "$NURSE_LIST" | head -c 200`. A healthy API with an empty list is the one failure this app is prone to, and the only way to see it is to ask for the data.
Then update `lab.conf` — both values. `NURSE_MODE="compose"`, and `NURSE_ENV` pointing at whatever file the project actually loads. Several challenges edit `NURSE_ENV` to cause faults; if it still names `/etc/nurse/nurse.env` they will edit a file nothing reads, and the symptom is a challenge that appears not to work rather than a configuration that is wrong.
Leave room for `compose.override.yaml`. s5-04 writes one to impose a memory limit on the API, so the project has to be a normal one that compose merges overrides into — nothing special required, but do not name your base file `docker-compose.yml` and your override something compose will not pick up.
