The service is up whenever you look, and the developer's timestamps are roughly regular. Before testing any theory about the database, establish whether the process is the same process it was an hour ago, or a different one.
Uptime per process, not per service: `docker inspect -f '{{.RestartCount}} {{.State.StartedAt}}'` on the api container, or `systemctl show -p NRestarts --value` for a unit. A restart counter climbing all afternoon says the process is being killed and restarted, not failing to reconnect.
Something is killing it. `sudo dmesg -T | tail -40` and `journalctl -k -S '2 hours ago'` are where the kernel records that, and the words to look for are `oom-kill` and `Memory cgroup out of memory`.
Read the OOM line carefully. It names the cgroup the kill happened in, and it is the API's own cgroup — which means the limit that was hit belongs to the API, not to the machine. The host has plenty of free memory, which is why nothing else is affected.
Find the memory limit on the api service — `mem_limit` in the compose file, or `MemoryMax=` in the unit — and compare it with what the process actually needs. It has been set far too low.
The sluggish box and the indexer are real but they are not the cause. Stopping the indexer frees memory on the host and changes nothing about a limit inside the API's own cgroup, so the API will keep dying. Both need dealing with; only one is the fault.
