Do the account and the keys first, and keep two sessions open: build and harden SSH from session one, test with session two. `sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication|pubkeyauthentication'` tells you what sshd will actually do, which is not always what the file you edited says — a drop-in in `/etc/ssh/sshd_config.d/` wins over the main file.
`ufw` before the applications, not after. `sudo ufw default deny incoming`, `sudo ufw allow` only the ports in `EXPECTED_PORTS`, then `sudo ufw enable` — and remember SSH is in that list before you enable it. Docker publishes ports past ufw by writing its own iptables rules, which is s4-04; bind containers to loopback and let nginx be the only thing listening publicly.
Order matters for the backups: seed the data, *then* take the archive. The suite restores the latest snapshot and compares its row counts against the live database, so an archive taken before `lib/seed.sh` ran will not match, and the failure will look like a broken restore when it is really a stale one.
The HTTPS assertions check each vhost by SNI, so one certificate has to carry all three names in its subjectAltName. `openssl x509 -in "$TLS_CERT" -noout -ext subjectAltName` shows what yours covers; SETUP.md section 8 has the command that makes it with all three.
The redirect assertion wants plain HTTP to answer 301 or 308, not to serve the page. One `server` block on port 80 with `return 301 https://$host$request_uri;` and the real blocks on 443.
`EXPECTED_PORTS` is checked in both directions, so a development server you left running fails it just as surely as a service that did not come back. `sudo ss -ltnp` names the process behind each one: capture the list when the machine is in the state you are willing to defend, and put that in `lab.conf`.
The reboot is the assertion most rebuilds fail. Everything started by hand works until the machine stops; `systemctl is-enabled` on every unit you created — including `docker` and the backup timer — before you reboot, not after.
