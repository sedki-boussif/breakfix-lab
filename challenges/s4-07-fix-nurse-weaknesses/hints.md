Find out which settings module the deployment actually loads before editing anything: `DJANGO_SETTINGS_MODULE` in `/etc/nurse/nurse.env`, and then read that file. The repository has duplicate files at its root; the canonical ones are under the application directories.
The pattern to remove looks like `os.environ.get('SECRET_KEY', 'django-insecure-...')` or `config('SECRET_KEY', default='...')`. The fix is to remove the default so the lookup raises.
For `DEBUG`, the pattern is usually `os.environ.get('DEBUG', 'True')` or a truthiness test that treats an unset variable as true. The fix is a default of false, and a parse that only accepts an explicit affirmative — `'true'`, `'1'`, `'yes'` — rather than treating any non-empty string as true. Note that `bool('False')` is `True` in Python, which is how this bug is usually written.
Make the failure loud and specific. `raise ImproperlyConfigured("SECRET_KEY is not set")` tells whoever deploys it exactly what to do; a bare `KeyError` traceback does not.
Test the refusal before you test the success: with the variable unset, the app must fail to start. `sudo systemctl stop nurse-api`, then run the check command by hand with the variable removed from the environment.
Keep the diff to the settings file. A commit that also reformats, renames, or restructures is a commit nobody can review, and this one is going on a public repository with your name on it.
